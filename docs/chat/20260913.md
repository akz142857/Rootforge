我的当前理解：

- Rootforge 是事件驱动的无人值守事故调查与受控修复系统，不是 `ask` 式运维聊天工具。
- 核心闭环是：`Trigger → Incident Case → Evidence → Analyzer → Correlation → Harness Agent → RCA → Forge → Policy/Action → Notification`。
- Harness Agent 必须自研；HolmesGPT 只作为竞品和评测基线，不是运行依赖。
- L1 是 `Evidence Acquisition`，不是日志平台：有 Loki/ELK 就按 Case 查询；没有则通过受限 Retriever 按需取证。
- 所有结论必须区分 `Fact / Inference / Unknown`，并引用可追溯证据。
- 调查可以无人值守，但生产写操作默认拒绝；Harness 只能提议，Policy 授权，Action Executor 执行。
- 技术栈采用 Go-first；未来只有明确性能或隔离需求的 Analyzer 才考虑 Rust。
- v0.1 聚焦 Docker/Swarm 环境的 JVM OOM，`hprofx` 是当前最有价值的真实资产和差异化能力。

这个拆分更合理：**Harness Agent 独立仓库、独立版本、独立测试；Rootforge 作为领域应用接入它。**

但“独立开发”不等于一开始就拆成远程服务。v0.1 建议：

```text
独立 Git 仓库 / Go module
        ↓ Go SDK
Rootforge 进程内嵌入
        ↓
未来按需升级为独立 Worker / gRPC 服务
```

职责边界应这样划分：

| 独立 Harness Agent | Rootforge |
|---|---|
| Agent 运行循环与终止条件 | Incident 检测、聚合和调度 |
| Planner、Hypothesis、Evaluator | Incident Case 和 Evidence Ledger |
| 模型 Provider 抽象 | Docker、Loki、hprofx、Git 等工具实现 |
| Tool-call 协议 | Case 级工具授权和执行 |
| Token、步骤、时间、成本预算 | 数据访问策略和生产凭证 |
| Checkpoint、恢复、事件流 | RCA、Finding、Evidence 的持久化 |
| 结构化输出验证 | Forge、Policy、Action、Notification |
| 通用审计事件 | Rootforge 领域审计和自动化策略 |

最重要的安全边界是：

```text
Harness Agent
    → 请求调用 tool
Rootforge Tool Gateway
    → Case 范围检查
    → Policy 检查
    → 执行只读工具
    → 保存 Evidence
    → 返回结构化结果
Harness Agent
    → 继续推理
```

Harness 不能直接持有 Docker、GitHub、生产数据库或云平台凭证，也不能自行执行 Shell。它只知道“有哪些工具可调用”和“工具返回了什么”。

建议独立模块提供类似这样的公共接口：

```go
type Runtime interface {
    Run(
        ctx context.Context,
        request RunRequest,
        tools ToolExecutor,
        events EventSink,
    ) (RunResult, error)
}

type RunRequest struct {
    RunID       string
    Objective   string
    Context     []ArtifactRef
    Tools       []ToolDescriptor
    Budget      Budget
    OutputSchema json.RawMessage
}

type ToolExecutor interface {
    Execute(context.Context, ToolCall) (ToolResult, error)
}
```

Rootforge 负责适配：

```text
Incident Case
    → RunRequest
Evidence / Finding / ContextGraph
    → ArtifactRef
Rootforge Tool Registry
    → ToolExecutor
Harness RunResult
    → RCA / Escalation
Harness Events
    → Case history / Audit
```

还要避免两个常见问题：

- 不让独立 Harness 的 API 出现 `IncidentCase`、`OOM`、`RCA` 等 Rootforge 专属类型；Rootforge 通过输入和输出 Schema定义这些领域语义。
- 不让 Harness 和 Rootforge 各自维护一套权威调查状态。Harness 只拥有运行时 checkpoint，Rootforge Case 始终是事故事实和审计记录的最终来源。

因此，现有文档中的“Rootforge 自研 Harness Agent”可以调整为：

> Rootforge 使用团队独立开发、独立发布的 evidence-driven Harness Agent；Rootforge 拥有事故领域模型、工具、证据、权限和行动边界，Harness 只拥有通用 Agent 执行与推理运行时。

下一步最适合先做一份独立 Harness 的产品边界和 `protocol/v1` 契约，然后再创建仓库；暂时不写模型推理逻辑，也不急着部署为网络服务。
