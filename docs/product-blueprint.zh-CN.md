# Rootforge 产品定位蓝图

> **Find the root. Forge the fix.**

## 一句话定位

**Rootforge 是一个开源、无人值守、证据驱动的生产事故调查与修复系统：它从生产事件自动建立案件，把异常连接到实际部署版本、Git 提交和源代码，生成可验证的根因分析，并按策略准备修复或通知开发者。**

更短的表达：

> **Detect the incident. Find the root. Forge the fix.**

## 我们解决什么

生产事故发生后，工程师通常需要在多个相互割裂的系统之间手工拼接事实：

```text
告警和指标
    +
主机、容器和 JVM 现场
    +
应用日志与调用链
    +
部署记录和镜像信息
    +
Git 提交
    +
源代码与最近变更
    =
一次耗时且高度依赖个人经验的事故调查
```

监控系统能说明“哪里出现了异常”，Coding Agent 能阅读和修改代码，但二者之间缺少一条可靠的连接：

```text
Production Runtime
        -> Service / Container
        -> Image / Build
        -> Git Repository / Commit
        -> Relevant Code
        -> Root Cause
        -> Fix
```

**Rootforge 要解决的核心问题，就是打通这条 Runtime-to-Code 调查链。**

它不只总结日志，而是收集、关联和验证来自运行时、部署历史和代码仓库的证据，回答：

1. 发生了什么，影响了谁？
2. 当时实际运行的是哪一个版本？
3. 哪些运行时证据解释了故障机制？
4. 哪段代码、配置或最近变更最可能造成问题？
5. 结论的可信度有多高，还有哪些反证或未知项？
6. 应该如何修复，以及如何验证修复有效？
7. 当前策略是否允许自动处理，还是必须携带完整上下文通知开发者？

## 目标用户

Rootforge 首先服务于需要亲自处理线上事故的技术团队：

- 维护 Docker、Docker Swarm 或 Kubernetes 服务的后端工程师
- SRE、DevOps 和平台工程师
- 没有专职 SRE、由研发轮值处理事故的中小团队
- 希望把内部事故经验沉淀为可重复诊断能力的工程组织

早期用户应同时具备三个条件：

- 有真实生产环境和重复发生的事故
- 服务与 Git 仓库、构建产物之间能够建立映射
- 愿意让系统读取有限的运行时证据和源代码，并用明确策略控制自动修复边界

## 用户购买的不是“AI”，而是调查结果

一次有价值的 Rootforge 调查，最终应交付：

- 明确的事故摘要、影响范围和时间线
- 一个可复现、可归档的证据包
- 实际部署的服务、镜像、构建和 Git 提交
- 按可信度排序的根因候选
- 每个结论对应的支持证据、反证和未知项
- 相关代码文件、符号、配置和最近变更
- 修复建议、风险以及验证步骤
- 根据仓库和环境策略生成的补丁、Pull Request 或受控处置记录

因此，Rootforge 的核心输出不是聊天记录，而是一个**可审查的 Incident Case**。

## 核心产品循环

```text
Detect
无人值守接收事故事件
   |
   v
Acquire
从授权数据源按 Case 和预算获取有限证据
   |
   v
Correlate
把节点、容器、镜像、构建、提交和代码连接起来
   |
   v
Investigate
提出假设，用证据验证或排除
   |
   v
Report
生成带可信度、证据和未知项的 RCA
   |
   v
Forge
提出修复、测试，并交给策略判断能否执行
   |
   v
Act or Notify
执行允许的动作；否则携带完整 Case 通知开发者
   |
   v
Learn
把已确认结论沉淀为下一次可复用的诊断规则
```

产品长期价值来自这个循环不断积累的组织知识，而不只是单次调用模型的结果。

## v0.1：JVM OOM Investigator

第一版只解决一个具体问题：

> **Java 服务发生 OOM 后，在不等待人工提问的情况下自动建案、组织事故现场、分析 JVM heap dump，并将内存异常关联到框架状态、配置和源代码，生成可执行的 RCA 并通知开发者。**

今天发生的 RabbitMQ OOM 是第一个真实基准案例：

- `byte[]` 占据大部分堆内存只是表象
- `ConsumerWorkService` retained 约 810 MB，指向客户端消息积压
- 约 47,584 条消息占用约 749 MB
- 对象字段显示 `ackMode=NONE`，解释了 prefetch 为什么没有形成预期反压
- 线程栈进一步揭示消费者锁竞争和业务处理变慢
- 单次加载 114,212 行数据构成次要内存放大因素

这个案例展示了 Rootforge 与普通 heap histogram 或日志总结工具的差别：

> **普通工具告诉你什么对象很大；Rootforge 应该告诉你为什么会变大、哪个运行状态或配置造成了它，以及应该去哪里修。**

### v0.1 输入

- OOM 时间、服务、容器和节点信息
- 内核、容器和应用日志
- JVM heap dump 与线程信息
- 镜像标签、构建元数据和部署记录
- Git 仓库、部署提交及其最近变更
- 可选的内存指标和请求量时间序列

### v0.1 输出

- 标准化事故概览和时间线
- Heap 概览、主要持有者、retained size 和 GC root 路径
- 框架感知分析，例如 Spring AMQP 消费者状态与配置
- 运行时对象、线程行为和代码语义之间的关联
- 根因候选、可信度、支持证据、反证和未知项
- 推荐修复及验证清单
- Markdown 和机器可读格式的 Incident Case

### v0.1 成功标准

Rootforge 不以“生成了一份很长的报告”为成功。首个里程碑需要满足：

- 对已知 RabbitMQ OOM 案例稳定复现关键结论
- 从接收到事故事件到首份报告不需要人工发起调查
- 报告中的关键事实都能追溯到原始证据
- 根因结论能定位到具体框架配置、代码路径或部署变更
- 另一位未参与事故的工程师可以依据报告理解问题并实施修复
- 系统清楚区分事实、推断和未知信息，不伪造缺失证据

## 我们明确不做什么

清楚的边界比能力列表更重要。Rootforge 在早期不是：

- 另一个 Prometheus、Grafana、Datadog 或通用 APM
- 日志、指标和 Trace 的长期存储平台
- PagerDuty 或 incident.io 式的值班与事故流程管理系统
- 部署在每台服务器上、拥有无限 Shell 权限的大模型 Agent
- 只把日志粘贴给 LLM 的聊天界面
- 通用的 Java heap dump GUI 或 Eclipse MAT 替代品
- 允许 Agent 绕过策略、审批或审计直接修改生产系统的平台
- 面向所有故障类型、所有语言和所有基础设施的第一版产品

Rootforge 应复用现有观测与代码工具，把差异化能力集中在**证据关联、框架感知诊断和 Runtime-to-Code 映射**上。

## 产品差异化

### 1. Runtime-to-Code 映射

Rootforge 必须可靠回答“出问题的容器运行的是哪份代码”，而不是让模型猜测仓库和版本。

### 2. 证据驱动，而不是一次性生成结论

每个关键结论必须注明来源，并区分：

- `Fact`：直接观察到的事实
- `Inference`：基于事实得出的推断
- `Unknown`：当前缺失、需要补充的信息

### 3. 框架感知诊断

通用工具发现“大对象”或“慢线程”；Rootforge 的 Analyzer 读取框架内部状态，理解 Spring AMQP、HikariCP、Netty 等组件的配置和运行语义。

### 4. 调查过程可复现

相同的证据包应能重复运行分析。模型、规则和工具版本需要被记录，便于审计与比较。

### 5. 策略控制修复边界

自动化程度按风险逐步提升：

```text
自动发现 -> 自动取证 -> 自动调查 -> 建议修复 -> 生成补丁 -> 运行测试
                                                      |
                                      策略允许则执行，否则通知开发者
```

生产环境变更不属于 v0.1 范围，但从一开始就保留独立的 Policy 与 Action 边界。

## 产品形态

Rootforge 由以下核心组件构成：

| 组件 | 职责 |
| --- | --- |
| Trigger | 接收并标准化 OOM、告警、崩溃、发布等事故事件 |
| Incident Controller | 去重、聚合、建案并调度无人值守调查 |
| Evidence Access | 从现有系统或节点按需获取有限证据 |
| Case | 保存一次事故的标准化事实、证据、分析过程和产物 |
| Analyzer | 对 heap dump、线程、框架状态、部署和代码进行确定性分析 |
| Harness Agent | 自研 Agent 执行框架，编排工具、提出和验证假设，生成 RCA |
| Forge | 生成候选修复并在隔离环境验证 |
| Policy / Action | 决定并执行明确允许的动作，支持验证与回滚 |
| Notification | 无法安全自动推进时把完整 Case 发送给开发者 |

其中现有的 `hprofx` 可以成为第一个 JVM Analyzer。它的长期定位不是单独竞争通用 heap dump 工具，而是为 Rootforge 提供框架感知的 JVM 现场证据。

组件如何组成完整系统，以及各层的权限与责任边界，详见[系统分层与边界](system-layers.zh-CN.md)。

## 发展路径

### 阶段一：无人值守发现、调查与通知

- 接收 Docker OOM 或测试事件并自动建立 Case
- 保留手工导入作为离线重放和测试入口
- 完成 JVM OOM Incident Case
- 集成 `hprofx`
- 输出证据驱动的 RCA
- 自动通知开发者，无需先输入问题

### 阶段二：自动取证与关联

- 接收 Docker 或监控告警
- 从现有数据源自动获取事故时间窗内的有限证据
- 建立镜像、构建和 Git 提交映射
- 自动运行相关 Analyzer

### 阶段三：准备修复

- 根据 RCA 生成候选补丁
- 在隔离环境运行测试与回归验证
- 根据仓库策略创建 GitHub Pull Request 或请求审批

### 阶段四：受控自动修复

- 执行白名单内、幂等、可逆的低风险操作
- 自动验证处置效果
- 验证失败时回滚并通知开发者

### 阶段五：扩大诊断覆盖

- JVM 内存泄漏与 GC 异常
- Crash 和 Restart Loop
- CPU 饱和与线程死锁
- 磁盘耗尽、5xx、超时和数据库连接池耗尽
- Kafka、HikariCP、Netty 等新的框架 Analyzer

## 北极星指标

早期最重要的指标是：

> **Rootforge 独立完成、且最终被工程师确认有用的事故调查数量。**

辅助指标包括：

- 从事故发生到首份可信 RCA 的时间
- 报告中有原始证据支持的关键结论比例
- 根因候选被工程师确认的比例
- 调查过程中需要的人工操作次数
- 修复建议被采用或转化为 PR 的比例
- 同类事故再次发生时诊断时间的下降幅度

模型调用次数、报告长度和生成代码量都不是核心成功指标。

## 当前产品承诺

对 Rootforge v0.1，最诚实也最有力量的承诺是：

> **生产中的 Java OOM 一旦发生，Rootforge 无需等待工程师提问，就会自动建案并把“什么占满了内存”推进到“为什么它会积压、哪项配置或代码造成了它、应该如何验证和修复”；能够安全推进则准备处置，否则携带完整证据通知开发者。**

这就是 Rootforge 要先解决的问题。
